# Safe Deployment From Zero 🚀

### راهنمای عملی انتشار کم‌ریسک اپلیکیشن؛ از CI/CD تا Rollback

ساختن اپلیکیشن فقط بخشی از ماجراست. وقتی کاربران واقعی از سرویس استفاده می‌کنند، هر انتشار جدید می‌تواند روی دسترس‌پذیری، تجربه کاربری و حتی فروش تأثیر بگذارد.

در این Repository چهار راهکار کاربردی برای **Safe Deployment** را با یک اپلیکیشن نمونه یاد می‌گیریم. هدف این است که به‌جای حفظ کردن اصطلاحات، هر مفهوم را مرحله‌به‌مرحله اجرا، آزمایش و نتیجه‌اش را مشاهده کنیم.

> **Safe Deployment به معنی انتشار بدون هیچ خطا نیست؛** یعنی ریسک تغییرات را کاهش دهیم، مشکل را زودتر شناسایی کنیم و برای بازیابی سرویس آماده باشیم.

## مسیر یادگیری

### 01 — CI/CD Pipeline

در گام اول یاد می‌گیریم چطور بعد از تغییر کد، فرایند **Build** و **Test** به کمک GitLab CI/CD به‌صورت خودکار اجرا شود. یک تست ناموفق را هم شبیه‌سازی می‌کنیم تا ببینیم Pipeline چطور از ادامه فرایند جلوگیری می‌کند.

**مفهوم کلیدی:** قبل از انتشار، تغییرات باید به‌شکل تکرارپذیر بررسی شوند.

[ورود به مرحله اول](./01-ci-cd/)

### 02 — Staging Environment

در این بخش با Docker Compose یک محیط **Staging** جدا از **Production آزمایشی** می‌سازیم. نسخه جدید را ابتدا در Staging اجرا می‌کنیم و با Smoke Test رفتار اصلی اپلیکیشن را بررسی می‌کنیم.

**مفهوم کلیدی:** تا حد امکان قبل از اثر گذاشتن روی کاربران واقعی، نسخه جدید را در محیطی مشابه Production آزمایش کنیم.

[ورود به مرحله دوم](./02-staging/)

### 03 — Canary Deployment

در این بخش دو نسخه از اپلیکیشن (`v1` و `v2`) را هم‌زمان اجرا می‌کنیم و با **NGINX Weighted Load Balancing**، بخشی از درخواست‌ها را به نسخه جدید می‌فرستیم؛ برای مثال وزن‌های `95` برای `v1` و `5` برای `v2`. سپس همین مفهوم را در Kubernetes با **Gateway API / HTTPRoute** بررسی می‌کنیم.

**مفهوم کلیدی:** به‌جای انتقال یک‌باره همه ترافیک، نسخه جدید را ابتدا در مقیاس محدود ارزیابی کنیم.

> توزیع وزنی درخواست‌ها لزوماً معادل اختصاص دقیق ۵٪ از کاربران یکتا نیست. در Kubernetes نیز اجرای مثال به Gateway Controller سازگار نیاز دارد.

[ورود به مرحله سوم](./03-canary/)

### 04 — Health Checks, Monitoring & Rollback

در گام آخر، وضعیت نسخه جدید را با Health Check و معیارهای خطا بررسی می‌کنیم. یک سناریوی خرابی کنترل‌شده می‌سازیم تا نشان دهیم چگونه می‌توان **Rollout را متوقف** کرد و با برنامه Rollback، ترافیک را به نسخه سالم قبلی برگرداند.

**مفهوم کلیدی:** انتشار امن فقط تست قبل از Deploy نیست؛ تشخیص مشکل و بازیابی پس از انتشار هم ضروری‌اند.

> Rollback خودکار نیازمند پیکربندی صریح است. بازگرداندن نسخه اپلیکیشن هم همیشه تغییرات دیتابیس یا داده‌های کاربران را به وضعیت قبل برنمی‌گرداند.

[ورود به مرحله چهارم](./04-monitoring-rollback/)

## پیش‌نیازها

- آشنایی اولیه با Git و مفاهیم HTTP
- Docker و Docker Compose برای آزمایش‌های محلی
- GitLab و یک GitLab Runner مناسب برای اجرای بخش CI/CD
- NGINX برای سناریوی Canary محلی
- برای بخش اختیاری Kubernetes: یک کلاستر آزمایشی، `kubectl` و Gateway Controller سازگار

پیش‌نیازها و دستورهای دقیق اجرای هر آزمایش، داخل README همان دایرکتوری نوشته خواهند شد. برای یادگیری Canary محلی، نیازی به راه‌اندازی Kubernetes نیست.

## این پروژه چه چیزی نیست؟

این Repository یک **لابراتوار آموزشی** است، نه یک پلتفرم آماده Production. در محیط واقعی، موضوعاتی مثل Secret Management، کنترل دسترسی، Backup، سازگاری Migration دیتابیس، مشاهده‌پذیری، ظرفیت و فرایند Incident Response باید متناسب با سرویس طراحی شوند. همچنین اجرای همه روش‌های معرفی‌شده برای هر اپلیکیشن الزامی نیست.
